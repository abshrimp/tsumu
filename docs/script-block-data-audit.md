# スクリプトの最小ブロック設計・全31種類の棚卸し

## 実装状況：ブロック中心の整理（2026-11-07）

ユーザーの意図は「加工モーダルに機能を追加する」ことではなく、**最小限のブロックを組み合わせてあらゆる処理を表現すること**。

今回の変更では、通常のスクリプトパレットを **きっかけ6・動作16** に整理した。新しい「値を加工する」は普通のスクリプトブロックであり、**1ブロックが1つの値操作**を担う。前段の出力変数を次のブロックの入力変数にすれば、上から順に加工できる。入力変数と出力変数を同名にすれば、変数を増やさずに複数のブロックを連結できる。

- 「変数に値を入れる」は従来どおり文字列・変数参照の代入に使う。
- 「値を加工する」は型付きの純粋な操作を1件適用し、新しい値を変数に保存する。数値・文字列・JSON・リスト・条件の加工は、この**ブロックを縦に重ねて表現**する。新規の値の組み立てモーダルは使用しない。
- 「リスト表示を操作する」は、絞り込み・並べ替え・解除の3操作を1つのパレット入口から選べる。既存の保存種別は維持する。
- 計算、文字列分割、結合、旧件数、リスト内検索、リスト項目追加、置換、区切り付きリスト編集など従来の10種類は、通常一覧には表示せず「以前のブロックを表示」または検索で選べる。既存ドキュメントの読み込み・編集・実行は維持する。
- 旧「値を組み立てる」のrecipeを持つ保存済みブロックだけは、移行前のデータを失わないよう従来の編集画面を開ける。**新規利用の中心は通常のスクリプトブロック**。

実行上の区別：値を加工するブロックは元データを変更せず、出力変数を更新する。HTTP通信・ページ遷移・DOM操作・ストレージ変更は値の加工へ統合しない。値の種類が違う、条件に合うものがないなどのときは、レシピの規則に従ってエラー・missingを返し、エラー時は出力変数を書き換えない。

今後も **旧ブロックの互換性が検証されるまで内部形式や読み込み処理を削除しない**。通常一覧は既に小さくなったが、従来のcount・array-find・array-field・calcなどを「同等」とみなして移行する段階ではない。

詳細：[ブロックの組み合わせ](script-block-composition.md)。

## 結論

「必要なブロック数」はコード内のScriptStep.kind数ではなく、**利用者が操作一覧で選ぶ種類の数**で数える。旧形式のkindは読み込み互換性のため残す。

- **目標：きっかけ6種類＋動作15種類程度。** 現行の25動作から、純粋な値加工8種類を「値を組み立てる」へ移し、リスト表示操作3種類を1種類にまとめた場合。あくまで機能等価性を達成したあとの目標で、現状の実装で15種類にできたわけではない。
- 値の加工はブロック数を増やさず、値入力の中で**型付きの操作を順に合成**する。
- 外部に影響する**通信・画面操作・保存・ナビゲーション**と、順序を持つ**条件分岐・待機・繰り返し**は動作ブロックに残す。
- UIをただ一種類の巨大な切替ブロックにするのは逆効果。「1つの動作で1つの効果」「値は組み立て可能」を維持する。
- **現時点で無条件に削除できる独立動作ブロックは0件。** 一見重複するものにも、副作用・スコープ・戻り値の違いがある。まず表現能力を移植してからパレットを整理する。

## きっかけ：6種類を維持

| きっかけ | 方針 | 理由 |
| --- | --- | --- |
| click | 維持 | 操作した時点で動く |
| hover-start | 維持 | ホバー開始時だけ動く |
| hover-end | 維持 | ホバー終了は開始とは別イベント。表示した要素の扱いも異なる |
| change | 維持・文言改善候補 | 入力・選択値が変化した時点 |
| load | 維持 | ページの読み込みとサーバー側データ取得に関係する |
| in-view | 維持 | IntersectionObserver系の表示領域への到達イベント |

「ホバー開始・終了」を切替選択肢に統合するのは、パレットを減らしてもきっかけの意味を見つけにくくする恐れがあるため、優先しない。将来のキーボード・フォーム送信・タイマーは必要性を確認してからイベントの設定項目として検討する。

## 動作：25種類の判定

記号：**残す**＝独立した意味があり維持、**値へ**＝値の合成が同等になればパレットから段階的に退避、**表示へ**＝リスト表示操作をまとめる、**条件付き**＝置換先の実行スコープや副作用が揃うまで保留。

| 現行キー | 判断 | 最小構成での居場所 | 移行前に守るべき性質 |
| --- | --- | --- | --- |
| fetch | 残す | データ取得 | HTTPメソッド・失敗・非同期・サーバー側時点・送信の副作用 |
| show / hide / toggle | 残す（現行パレットで統合済み） | 要素の表示変更 | 表示／非表示／切替とCSSの表示状態 |
| open-page / open-url | 残す（パレットで統合済み） | ページ・URLを開く | ルーティング、外部URL、別タブ |
| scroll-to | 残す | 指定要素へスクロール | 画面の副作用、対象選択 |
| set-value | 残す | 入力欄に値を設定 | 入力型の正規化、DOM入力と変数は別 |
| set-enabled | 残す | 入力の有効／無効 | disabled状態と反転 |
| split | 値へ | 文字列をリストに分ける | 区切り未指定はカンマ、trim、空要素を除外 |
| join | 値へ | リストを文字列につなぐ | 項目指定、空値処理、取得配列・各行のスコープ |
| count | 値へ・条件付き | リストの件数 | **表示絞り込み後の件数**、取得見本の先頭20件制限・元件数、非配列は0 |
| array-find | 値へ・条件付き | リストから条件に合う1件を探す | fieldパス、文字列比較、URL slug、見つからないときnull |
| array-field | 値へ・条件付き | 各項目を変換／項目を設定 | 同じ配列への更新、繰り返し中の対象、コピーと参照、サーバー実行制限 |
| for-each | 残す | リスト各項目を繰り返す | 項目スコープ・処理順・副作用。純粋なmapとは別 |
| filter-array | 表示へ | リスト表示を変更 | 表示対象のみ絞る。元の配列データは不変 |
| unfilter-array | 表示へ | リスト表示を変更 | 指定番号の解除／全解除、既存フィルターの保持 |
| sort-array | 表示へ | リスト表示を変更 | 表示順だけ変更。元データのソートとは別 |
| store-save | 残す | ブラウザに保存 | 永続化・同一オリジン・共有クッキーとストレージの順序 |
| store-load | 当面残す | 保存した値を読み込む | 読み出す時点・欠落時既定値・共有ドメイン・その後の変数代入 |
| set-var | 残す（中核） | 変数に値を入れる＋値を組み立てる | 変数名・評価時点・既存文字列テンプレート・値の型・名前変更 |
| calc | 値へ | 計算式を作る | 四則演算・括弧・ゼロ除算・従来の暗黙の数値変換との差 |
| replace | 値へ | 文字列を置換する | 正規表現・置換の$1・不正な式・テンプレート展開 |
| list-edit | 値へ・条件付き | 文字列分割→リスト要素追加／削除→結合 | **JSONリストではなく区切り文字付き文字列**、重複排除・空項目除外・toggle |
| copy | 残す | クリップボードにコピー | 権限・ブラウザのユーザー操作 |
| wait | 残す | 指定時間待つ | 次の動作の実行順・キャンセル |
| if | 残す | もし〜なら | 条件評価・AND/OR・スコープ、else |
| repeat | 残す | 回数指定／無限繰り返し | 停止・待機・実行キャンセル |

補足：内部のScriptStepにはshow/hide/toggleやopen-page/open-urlなども別kindで保存されるが、UIの動作一覧ではすでに1種類なので「統合による削減数」には加えない。

## 機能が足りない部分（新ブロックより先に値側へ追加）

優先順に並べる。型と失敗の扱いを決めるまでボタンだけ増やさない。

| 優先 | 値の加工として足すもの | 解消できること | 注意点 |
| --- | --- | --- | --- |
| P0 | 数値演算（＋−×÷％）・比較（=、大小）・AND/OR/NOT | calcと多数の単純なif条件を1つの値から扱える | 型変換・短絡評価・0/false/nullを混同しない |
| P0 | 文字列の分割・結合・置換 | split、join、replaceの代替に必要 | 空項目と正規表現の仕様差 |
| P1 | リストのfind・filter・map・sort | array-find、array-fieldの一部や複雑なデータ加工 | 「リスト表示」の絞り込みとは分離、項目のスコープと型 |
| P1 | 項目の設定・削除、リストの追加・削除 | 値を加工する実用性を高める | 元データを破壊しないコピー、存在しない階層の扱い |
| P1 | 値の種類を調べる・型を変える・null/missing判定 | 不意の0や空文字化を避ける | missingとnullの厳密な区別、入力チェック |
| P2 | ストレージの値を参照する入力源 | 将来store-loadを値の参照へ | ブラウザ限定・読み込み時点・共有cookie |
| P2 | フォーム送信・キーボード操作・時間経過のイベント | 今は別の工夫が要る操作 | 増やすならきっかけ設定で表現し、乱立させない |
| P2 | 明示的な失敗時の分岐・通知 | HTTP失敗や計算エラーを画面で扱う | 成功・失敗・キャンセルを区別 |

## 理想形でのパレット15動作

現行維持の14種類は以下の役割を持つ：**データ取得、変数へ代入、表示変更、ページ移動、スクロール、入力欄への代入、入力の有効／無効、ブラウザ保存、保存値の読込、クリップボード、待機、条件分岐、回数繰り返し、リスト各項目で繰り返し。**
それに**リスト表示を変更**（絞り込み・並べ替え・解除を一つの操作群にする）を加えて15種類。

一つの「リスト表示を変更」では順序依存を隠さず、フィルターとソートを同時に適用するなら実行順を明示する。UIが複雑なら当面は3操作のまま維持し、**15という数字を達成するためだけの切替UI**は作らない。

## 今すぐ不要にできない理由と修正すべき点

1. **count vs 組み立てるlength**：lengthは配列そのものの長さ。従来countには表示フィルター・切り詰めサンプルの元件数があり、現段階で一致しない。
2. **array-find vs 値のfield/index**：fieldは直接キーを読むだけ。条件一致の検索とは別。見つからない値もnullとmissingで違う。
3. **array-fieldとfor-each**：前者はデータの項目を書き換えるが、後者は順番付きの動作。親スコープ・子スコープが不完全なまま1つにしない。
4. **list-editの名称**：現実には「区切り文字付き文字列の集合編集」。JSONリスト編集と思わせる名称・配置は改める。
5. **保存と公開の動作差**：値の組み立てがエディタで動くだけでは統合完了にしない。SSR、クライアント、ZIP・Next.js生成、Undo/Redoを揃える。
6. **きっかけの発生条件**：ページloadとクリック、入力changeを統合してはいけない。副作用を持つ動作も純粋な式へ隠さない。
7. **扱えない値を黙って変換しない**：null、missing、非数値、誤った正規表現、取得失敗を明示する。ただし既存スクリプトの結果は互換モードで守る。

## 実装順序（減らす前の完了条件）

1. **基盤の安定化**：#134の検索UIテスト、#136の値の保存・評価、#137の候補クローズ、必要なPR依存関係・競合を解消。
2. **P0値加工を追加**：四則演算・比較・分割・結合・置換を同じ型付き式／保存形式／評価規則で実装。説明は要点だけ、操作名で探せるようにする。
3. **旧ブロックとの同等性テスト**：実例ごとに旧版／新版でデータ、エラー、実行の時点を比較。特に20件超取得、フィルター適用、slug、正規表現、無限ループ中断、保存領域。
4. **純粋リスト加工**：map/filter/find/sort、要素と添字のスコープ、オブジェクトの項目設定を導入。データの加工と画面の表示状態は別々にテストする。
5. **パレットの移行**：新規追加候補のみ段階的に整理。既存のJSONにある旧kindの描画・実行・編集・公開コード生成は維持。必要なら「以前のブロック」から追加できる救済導線を用意。
6. **リスト表示操作の再設計**：フィルター解除を含む操作の統合を検証。スクリプトの順序／番号を壊さずに動く場合のみまとめる。

### 旧ブロックを非表示にできる検証ゲート

- 同じ入力で**既存の実行結果・副作用・順序**と一致する（意図的に仕様を変える場合は明示的な移行手段）。
- 取得データの20件超の実件数、0件、欠落/null、特殊なドット付き項目名、変数名変更、ネストしたリストを確認。
- **プレビュー／SSR／公開クライアント／生成Next.jsプロジェクト**が一致する。
- **保存→再読込→Undo/Redo→複製→エクスポート→再インポート**の往復が通る。
- フィルター/ソートの表示状態・複数条件・解除が保たれる。
- 既存文書の移行をするなら事前バックアップ、復元手順、後方互換の旧読み込み実装を確保。

**監査の結論：** 今の25動作は急いで消さない。値の組み立てで純粋なデータ操作を担えるようにし、機能の同等性が証明できたところから、一覧だけを小さくする。これなら最小構成を目指しつつ保存済みサイトを破壊しない。
