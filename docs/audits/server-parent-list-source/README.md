# 配信済みの親項目とブラウザ側の配列名が重なる場合

## 再現と原因

ページを開くときに取得した `items` を外側リストにし、各項目の `tags` を内側リストで並べます。同名の `tags` をクリック時のスクリプトでも変更すると、Canvas は項目ごとの配列を使いますが、生成サイトでは全項目にページの配列が使われます。

内側の配列がブラウザで変わるというページ単位の判定だけでテンプレートを生成していたためです。サーバーで展開済みの親項目は、ブラウザで作る行のスコープには入っていませんでした。

## 修正範囲

- JSX の生成時だけ、ページ変数を含まない項目スコープを保持します。
- 親項目が配列のキーまたは根を持っていれば、その項目の配列をサーバーで展開します。空配列、null、非配列、ドット付きパスの未指定の子もページの配列で埋め戻しません。
- 親項目に根がなければ、従来のブラウザ側リストを使います。
- 生の取得配列、項目全体、未使用の項目を新たにブラウザへ渡しません。既存の絞り込み項目だけを `data-item` に保持します。
- ブラウザ側の行のテキストが同名のページ変数に先行展開される問題は、この変更に含めていません。

## 検証

新規11 unitのうち7件が修正前に失敗し、修正後は11件すべて成功しました。mainのネイティブ入力修正と統合したtreeで全1,105 unit、typecheck、i18n、エディタのWebpack本番ビルドが成功しました。

通常の部品なし/あり、繰り返しの読み込み、行内スクリプト、並べ替え・絞り込み・解除、ページ移動、保存文書の読み直し、空/null/非配列/未指定の根、ドット付きキー、プリミティブ配列、表示件数、3段の入れ子とブラウザ側の子リストを検証しています。通常のサーバーのみの生成プロジェクトは修正前と全ファイルが一致します。

ドット付きキーは、実際にブラウザ側と判定される根の変数を使う回帰を別に追加しています。通常のサーバー側静的フィルターの回帰とは分けており、ブラウザ側と判定される配列の静的フィルター対応を新たに保証する変更ではありません。

生成したNext.jsプロジェクトは未変更のままコンパイルと型検査に成功しました。架空の取得先を使うテストのため、そのままのプリレンダーはDNSで失敗します。取得モジュールだけを固定のテストデータに差し替えた本番ビルドは成功し、RSCを含む出力に正しい4行があり、未使用のprivate sentinelがないことを確認しました。生成した描画・ランタイムは差し替えていません。

Chromium回帰は実際のSettingsPanel、ScriptEditor、Canvas、保存ストアと生成ランタイムを使います。配列選択、文字列分割の入力、undo/redo、保存文書の再読み込み、プレビューの再入場、生成サイトの操作とページ移動を検証します。取得配列の代入そのものはunitのSSR/DOMモデル回帰でも検証しています。ネイティブテストはローカル未実行で、公式CIの成功が必要です。生成Next.js全体のハイドレーションを検証するテストではありません。

ローカルのNode.jsは24系で、宣言された26.12.1以上ではありません。対応バージョンで動く公式CIのcheck/e2eとCloudflare buildの成功を確認してからマージします。
